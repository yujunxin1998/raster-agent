# 工具注册中心：从"构建时拼接"到统一 Registry 的演进设计

> 范围：回答"要不要做统一工具注册中心 + 动态热重载 + 权限体系"，以及"怎么做才不是推倒重来"。
> 前置阅读：[Agent架构设计文档.md](Agent架构设计文档.md)、[中间件洋葱模型说明.md](中间件洋葱模型说明.md)（`GuardrailMiddleware`/`ToolAuditMiddleware` 已在其中说明）。
> 结论先行：**当前四类工具来源的拼接方式暂时不需要推倒重来**；真正值得投入的是 Skill 的热重载（唯一一处"改配置要重启进程"的真实痛点）、把权限判断收敛到解析阶段（省 token、便于排障），以及本次明确要求的 **MCP 兼容**——代码库里目前没有任何真实 MCP 客户端，所以"兼容"意味着把 `MCPToolProvider` 作为和 Skill/内置工具同等地位的一等来源**设计并实现在 Phase 1**，即使初始不配置任何 MCP Server 也不影响其余部分。多实例同步、快照回滚落库这类当前单进程部署用不上的能力仍然按需分阶段做，本文档给出每一步具体改哪些文件。

## 一、现状盘点（代码事实，不是猜测）

### 1.1 工具是怎么拼起来的

`build_lead_agent()`（[lead_agent.py:101-115](../src/agent_core/agents/lead_agent.py)）每次请求现造一次 Agent，工具集是字面量拼接：

```python
base_tools: list[BaseTool] = [
    save_memory, recall_memory,
    write_file, read_file, run_python, run_command, save_output_file,   # 内置沙箱工具
    *skill_manager.get_tools("general"),
    *skill_manager.get_tools("tool"),
    *skill_manager.get_tools("rag"),
    *skill_manager.get_tools("database"),
    *(extra_tools or []),         # 前端本次消息带的 tool_list，见 chat_ws.py:103-108
    build_task_tool(),            # 唯一的 subagent 分发工具
]
```

四类来源、四种生命周期，这个判断是对的：

| 来源 | 生命周期 | 当前实现 |
|---|---|---|
| 内置工具 | 进程级，随代码发布 | 模块级 `@tool` 函数 + 显式 import（[memory_tools.py](../src/agent_core/tools/memory_tools.py)、[sandbox_tool.py](../src/agent_core/tools/sandbox_tool.py)），无自动扫描 |
| Skill | 应用级，启动时全量扫描一次 | `SkillLoader.load()`（[skill_loader.py:36-63](../src/agent_core/skills/skill_loader.py)）只读 frontmatter，正文渐进式披露；`SkillManager.get_tools()` 每次现包一层 `StructuredTool`，不缓存 |
| 前端工具 | **单条消息级**，不是会话级——`tool_list` 挂在每条 `content` 里（[chat_ws.py:96-108](../src/api/websocket/chat_ws.py)），执行经 `ConnectionManager.send_tool_call_and_wait_response` 走 WebSocket 往返 15s 超时 |
| Subagent 分发 | 静态 dict，代码里改 | `_PROFILES`（[subagent_profiles.py:51-59](../src/agent_core/agents/subagent_profiles.py)），目前只有 `web-researcher` 一条，新增类型 = 加一条字典项 |

**没有 MCP**：代码里"MCP"目前只是借用了 MCP 的 JSON Schema 工具描述格式（`FrontendTool.inputSchema`/`outputSchema` 字段名，[custom_tool_converter.py:34-46](../src/agent_core/tools/custom_tool_converter.py)），没有连接任何真实 MCP Server，`pyproject.toml` 里也没有 `mcp`/`langchain-mcp-adapters` 依赖。**本次要求明确要兼容 MCP**，因此下文的 Provider 设计里 MCP 是从 Phase 1 就实现的一等来源（见 4.4 节），不是占位符——只是"实现完成"和"生产环境真的接了外部 MCP Server"是两件事，后者取决于 `MCP_SERVERS` 配置是否非空，配置为空时这条 Provider 只是一个空操作，不影响其余三类来源。

### 1.2 权限校验：比预想的更统一，有一处重复而非缺口

原方案草稿里猜测"只有 Skill 工具过 Guardrail，内置工具靠 Middleware，两条路径不一致"——读代码后这个判断需要修正：

- `GuardrailMiddleware.awrap_tool_call`（[middlewares/guardrail.py:35-61](../src/agent_core/middlewares/guardrail.py)）挂在中间件链上，覆盖 **Lead Agent 自己图上** 的全部工具调用（内置/Skill/前端/task，因为它们最终都走同一个 LangGraph `ToolNode`），拒绝时返回 `error ToolMessage` 短路，不抛异常。
- `SkillToolFactory._invoke`（[skill_tool_factory.py:121-128](../src/agent_core/skills/skill_tool_factory.py)）里还留了一次 Guardrail 调用——**实现阶段核实后，这不是可以清理的重复校验，必须保留**：`subagent_profiles.py` 的 `web-researcher` profile 会把 `web_search` 分类下的 Skill 工具直接塞进 `tools_factory`，经 `sub_agent_factory.py::run_subagent()` 执行；该函数现造的子 Agent **不挂任何中间件**（模块文档明确写了"`GuardrailMiddleware`/`LoopDetectionMiddleware` 都不在场"），所以对这条路径上的 Skill 工具而言，`SkillToolFactory._invoke` 内部这次校验是**唯一**的权限防线，删掉就是真实的权限校验空档，不是无害的去重。上一版文档草稿在这里判断错误，现已更正。

底层校验逻辑本身是统一的：`AllowlistGuardrailProvider.check()`（[allowlist_guardrail_provider.py:47-78](../src/agent_core/guardrail/allowlist_guardrail_provider.py)）按位 AND 两张表——`SkillSettingsStore`（技能开关）和 `ToolPermissionStore`（[tool_permission_store.py](../src/storage/tool_permission_store.py)，泛化的工具级拒绝名单，`scope` 字段已预留、当前统一传 `"default"`）。无 `user_id` 或存储异常时默认放行，这是刻意的容错取舍，不是 bug。

### 1.3 已经存在、可以直接复用的基础设施模式

- **`init_xxx()` / `get_xxx()` 全局单例**：`GuardrailProvider`、`SandboxProvider`、`SkillManager`、`ToolPermissionStore` 全部是这个模式——启动时 `init` 一次，运行期 `get` 拿单例，未初始化时 `raise RuntimeError`。这是项目一以贯之的基础设施接入方式，新的 Registry 应该沿用，不要另起一套风格。
- **`ToolFilterRegistry`**（[tool_filter.py](../src/agent_core/tools/tool_filter.py)）：进程内 `set[str]`，支持运行时 `register`/`unregister`，已经是"最小热更新"的先例——不需要重启就能改变某个工具是否对前端可见/是否落库。
- **`ToolAuditMiddleware`**（[tool_audit.py](../src/agent_core/middlewares/tool_audit.py)）：已经是统一执行入口的旁路审计，明确写了"等评估事件体系迁移过来，只需要把日志调用换成事件发射，中间件位置不用变"——即当前架构本身已经为"统一 Dispatcher"式的横切关注点留了口子，不需要再造一个新的 Dispatcher 类去包一层。
- **`SkillLoader` 的容错风格**：单个 Skill/字段解析失败只记 error 跳过，不中断整体加载——这正是"静态校验失败保留旧状态"思路的雏形，热重载设计会延续同一哲学。

### 1.4 真正的空白

- **无热重载**：`SkillLoader.load()` 只在 `SkillManager.__init__` 里跑一次（[main.py:210-216](../src/main.py)），改 `SKILL.md` 必须重启进程。`PromptRegistry`/`PromptLoader` 是同一个模式、同一个空白（[prompts/prompt_registry.py](../src/agent_core/prompts/prompt_registry.py)），但本文档聚焦工具，Prompt 热重载可以复用同一套机制，不在本次范围内展开。
- **无版本/快照概念**：工具集是"当次请求现算的一个 list"，没有 revision，出问题时无法回答"昨天这个请求到底看到了哪些工具"。
- **无统一裁剪**：`extra_tools` 直接和内置工具用同名覆盖合并（[custom_tool_converter.py:169-175](../src/agent_core/tools/custom_tool_converter.py) `tool_map[base_tool.name] = base_tool`，前端同名工具会**覆盖**内置工具，没有告警日志，也没有"高风险工具不允许被前端覆盖"这类策略）——这是本次梳理中发现的一个值得关注的点，见 4.3 节。

## 二、目标与非目标

**目标**（这次要解决的）：
1. 给四类工具来源一个统一、可审计的中间表示，消除"想查一个工具从哪来、什么权限"要翻四处代码的问题。
2. Skill 改动免重启（这是唯一有真实使用场景的热重载需求）。
3. 权限判断提前到"解析工具集"阶段，而不是只在执行时用 `GuardrailMiddleware` 兜底——省 token（不把用户看不到的工具 schema 喂给模型），也让"模型为什么看不到这个工具"这件事可追溯。
4. 堵住前端工具静默覆盖内置工具这个口子。
5. **兼容 MCP**：接入任意标准 MCP Server（stdio / streamable-http）不需要再改 `ToolRegistry`/`resolve_tools`/中间件链——只需要新增一份 Server 配置，`MCPToolProvider` 是和 Builtin/Skill 同等地位的一等来源，见 4.4 节。

**非目标**（GPT 原方案里超出当前规模的部分，明确不做或推迟）：
- **不引入 Postgres/Redis 做多实例注册表同步**。项目当前是单进程部署（`init_xxx`/`get_xxx` 全局单例模式本身就假设单进程），进程内不可变快照已经能拿到"读不加锁、原子切换"的全部收益。等真的要横向扩容了，再把 `ToolRegistry` 换成"本地缓存 + 订阅广播"，不需要现在设计。
- **不把每个 Subagent 拆成独立工具**。当前只有一个 `web-researcher` profile，`task(subagent_type, task)` 单一分发工具的形态是合适的（[subagent_profiles.py](../src/agent_core/agents/subagent_profiles.py) 模块文档已经解释过这个取舍），Registry 只需要把 `task` 当一个工具定义登记，profile 列表作为它的动态约束元数据。
- **不重建一个新的 ToolDispatcher 类去取代现有中间件链**。`GuardrailMiddleware → ToolAuditMiddleware → ToolErrorHandlingMiddleware → LoopDetectionMiddleware` 这条 `awrap_tool_call` 链本身就是统一执行入口，职责已经很清楚（见[中间件洋葱模型说明.md](中间件洋葱模型说明.md)）。重新包一层 Dispatcher 只会变成两套并行的"工具调用生命周期"管理逻辑。

## 三、统一工具定义：贴着现有类型做，而不是另起一套

GPT 原方案的 `ToolDefinition` 字段是合理的骨架，但要注意：**`SkillDefinition`（[skill_definition.py](../src/agent_core/skills/skill_definition.py)）和 `FrontendTool`（custom_tool_converter.py:34-46）已经是各自领域的"权威定义"**，不应该被一个新的通用 `ToolDefinition` 取代——那意味着要重写 `SkillToolFactory`/`CustomToolConverter` 的全部转换逻辑，风险和收益不成比例。

正确的分工是：`ToolDefinition` 是**只读的登记表条目**，由每个来源的 Provider 从自己的权威定义"投影"出来，执行仍然走原来的工厂：

```python
class ToolDefinition(BaseModel):
    model_config = ConfigDict(frozen=True)

    canonical_name: str          # "skill.rag.search_knowledge_base" / "builtin.sandbox.run_python" / "mcp.github.create_issue"
    model_name: str              # 模型实际看到的短名，如 "search_knowledge_base"
    description: str

    source_type: Literal["builtin", "skill", "frontend", "subagent", "mcp"]
    source_id: str               # 如 "skill:rag/search_knowledge_base"、"frontend:{client_id}"
    scope: Literal["application", "request"]   # 当前只用得到这两档，见下方说明
                                                # session 级暂不需要：前端工具本来就是 per-message
                                                # （chat_ws.py:96-108），没有真正跨消息存活的"会话工具"

    permissions_key: str         # 传给 AllowlistGuardrailProvider.check() 的 tool_name，通常等于 model_name
    frontend_visible: bool = True
    enabled: bool = True

    build_tool: Callable[[], BaseTool]   # 惰性构建，真正复用 SkillToolFactory/CustomToolConverter/build_task_tool
```

`scope` 只需要 `application`（内置/Skill/task，启动后就存在，所有请求可见）和 `request`（前端工具，只在携带它的这一条消息里存在）两档——不需要 `tenant`/`user`/`session`，因为代码库里没有租户概念，用户级权限已经由 `AllowlistGuardrailProvider` 在解析阶段处理，不需要在 `scope` 里再建一层。

`canonical_name` 的命名空间设计（`builtin.*`/`skill.*`/`frontend.*`）值得采纳——它能在 4.3 节提到的"前端工具覆盖内置工具"问题上派上用场：解析阶段发现 `model_name` 冲突时，可以按 `source_type` 优先级判定（例如内置 > Skill > 前端），而不是像现在这样谁后合并谁赢。

## 四、注册中心结构：进程内不可变快照，沿用项目已有单例风格

### 4.1 快照与注册中心

```python
@dataclass(frozen=True)
class RegistrySnapshot:
    revision: int
    created_at: datetime
    by_canonical_name: Mapping[str, ToolDefinition]
    by_model_name: Mapping[str, ToolDefinition]
    by_source: Mapping[str, tuple[str, ...]]   # source_id -> canonical_name 列表，删除来源时用


class ToolRegistry:
    def __init__(self) -> None:
        self._snapshot = RegistrySnapshot.empty()
        self._write_lock = asyncio.Lock()

    def current_snapshot(self) -> RegistrySnapshot:
        return self._snapshot   # 读不加锁，快照发布后不可变

    async def publish(self, source_id: str, definitions: list[ToolDefinition]) -> RegistrySnapshot:
        async with self._write_lock:
            candidate = self._snapshot.replace_source(source_id, definitions)
            _validate(candidate)   # 见 5.3 节；校验失败抛异常，_snapshot 不变
            self._snapshot = candidate
            return candidate


_registry: ToolRegistry | None = None

def init_tool_registry() -> ToolRegistry: ...
def get_tool_registry() -> ToolRegistry: ...
```

与项目其余单例（`GuardrailProvider`/`SandboxProvider`）保持同一接入方式：`main.py` 启动时 `init_tool_registry()`，各处 `get_tool_registry()`。

### 4.2 Provider：把现有四个来源各包一层薄适配

不重写现有工厂，只是让每个来源多产出一份 `ToolDefinition` 元数据：

| Provider | 数据来源 | `discover()` 实现要点 |
|---|---|---|
| `BuiltinToolProvider` | 显式清单（同 `lead_agent.py:101-108` 里那几行） | 硬编码 list，`build_tool` 直接返回已 import 的 `@tool` 函数 |
| `SkillToolProvider` | `SkillRegistry`（已有，[skill_registry.py](../src/agent_core/skills/skill_registry.py)） | 遍历 `registry.by_category(*)`，`build_tool = lambda skill=skill: skill_tool_factory.create(skill)`——**不改** `SkillToolFactory`/`SkillContentReader` 任何一行 |
| `FrontendToolProvider` | 每条消息的 `tool_list` | 不写入全局快照（见下），只在 `_handle_chat` 里构造一份临时 `list[ToolDefinition]`，`source_id = f"frontend:{client_id}:{conversation_id}"` |
| `SubagentToolProvider` | `_PROFILES` | 登记唯一一条 `subagent.task`，`build_tool = build_task_tool` |
| `MCPToolProvider` | 配置的 MCP Server 列表 | 真实实现，见 4.4 节——不是占位符 |

**前端工具不进全局 `ToolRegistry`**：这是对 GPT 原方案"Session Overlay Registry"的简化——既然前端工具本来就是 per-message 的（不是常驻 session），没必要为它单独维护一个"注册-注销"的 overlay 生命周期，直接在 `_handle_chat` 里现算一份 `list[ToolDefinition]`，和从 `registry.current_snapshot()` 取到的 application 级定义合并后一起送进解析器即可，合并时按 4.3 节的冲突策略处理。

### 4.3 解析层：把权限判断提前，并且堵住覆盖漏洞

```python
async def resolve_tools(
    *,
    snapshot: RegistrySnapshot,
    request_definitions: list[ToolDefinition],   # 本次前端工具，可能为空
    user_id: str | None,
    guardrail_provider: GuardrailProvider,
) -> ResolvedToolSet:
    merged = _merge(snapshot.by_model_name, request_definitions)  # 见下方冲突策略
    allowed: list[ToolDefinition] = []
    rejected: list[RejectedTool] = []

    for definition in merged.values():
        if not definition.enabled:
            continue
        decision = await guardrail_provider.check(
            user_id=user_id, tool_name=definition.permissions_key, tool_args={},
            context=GuardrailContext(conversation_id=None, thinking=False),
        )
        (allowed if decision.is_allowed else rejected).append(definition)

    return ResolvedToolSet(
        registry_revision=snapshot.revision,
        tools=[d.build_tool() for d in allowed],
        rejected=rejected,
    )
```

**冲突策略**（修正 1.4 节提到的问题）：`_merge` 按 `source_type` 优先级——`builtin` > `skill`/`subagent`/`mcp` > `frontend`。前端 `tool_list` 出现与内置/Skill/MCP 同名的 `model_name` 时，**丢弃前端定义并记 warning**，而不是像现在 `custom_tool_converter.py:169-175` 那样静默覆盖。这是本次梳理发现的唯一一处需要真正修代码行为的点，其余都是"抽一层适配"。`mcp` 排在 `frontend` 之前的原因见 4.4 节末尾的安全边界说明——MCP Server 是运维显式配置的可信来源，前端 `tool_list` 是请求方自报的，信任级别更低。

注意：这一层解析结果**不能替代** `GuardrailMiddleware`。原因是 `resolve_tools` 只在请求开始时跑一次，而一次多轮工具调用的会话中途，权限状态理论上可能变化（用户在另一个标签页关掉了某个技能）；`GuardrailMiddleware` 仍然是运行时的最终防线。两层的关系是：**解析层负责"要不要把这个工具的 schema 喂给模型"（省 token、体验更好），Middleware 负责"真正执行前的最终校验"（安全边界）**，职责不重叠，都要保留。

`ResolvedToolSet.registry_revision` 写入现有 `AgentRuntimeContext`（[middlewares/context.py](../src/agent_core/middlewares/context.py)），`ToolAuditMiddleware` 打日志时带上这个字段，就获得了"复现某次对话当时能看到哪些工具"的能力，不需要新的审计通道。

### 4.4 MCPToolProvider：真实设计，不是占位符

技术选型：`langchain-mcp-adapters`（LangChain 官方维护，包装 `mcp` Python SDK 的 `ClientSession`，直接产出 `list[BaseTool]`）而不是自己手写一遍 JSON Schema → Pydantic 的转换——`CustomToolConverter._schema_to_pydantic`（[custom_tool_converter.py:77-95](../src/agent_core/tools/custom_tool_converter.py)）是前端工具场景下不得不自己写的原因（协议只到"WebSocket 传一份 JSON"这一层，没有现成客户端库可用），MCP 场景不存在这个限制，没必要重复造轮子。新增依赖：`mcp`、`langchain-mcp-adapters`（`watchfiles` 已经在依赖树里，这两个不是）。

**配置**：仿照 `SKILLS_DIRS` 的风格加一项 `settings.py`，但 MCP Server 描述比"一个路径"复杂，用 JSON 而不是逗号分隔字符串：

```python
# settings.py，新增
MCP_SERVERS: str = os.getenv("MCP_SERVERS", "[]")
# 形如 [{"id": "github", "transport": "stdio", "command": "npx", "args": [...]},
#       {"id": "search",  "transport": "streamable_http", "url": "https://..."}]
```

配置为空（默认值）时 `MCPToolProvider.discover()` 直接返回空列表，其余三类来源完全不受影响——这就是"兼容 MCP"和"现在没有真实 MCP Server 也不影响其余部分"能同时成立的原因。

**连接生命周期**：新增一个 `MCPConnectionManager`（沿用项目 `init_xxx`/`get_xxx` 单例风格），应用启动时对配置里的每个 Server 建立 `ClientSession` 并保持常驻（`stdio` 是子进程，`streamable_http` 是长连接 HTTP session）：

```python
class MCPConnectionManager:
    async def connect_all(self, server_configs: list[MCPServerConfig]) -> None:
        for cfg in server_configs:
            asyncio.create_task(self._connect_with_retry(cfg))   # 各 Server 独立，一个连不上不阻塞其它

    async def _connect_with_retry(self, cfg: MCPServerConfig) -> None:
        backoff = 1.0
        while True:
            try:
                session = await self._open_session(cfg)
                self._sessions[cfg.id] = session
                self._status[cfg.id] = "connected"
                await self._publish_tools(cfg.id, session)
                await self._watch_disconnect(cfg.id, session)   # 阻塞到连接断开
            except Exception as exc:
                self._status[cfg.id] = "reconnecting"
                logger.warning(f"[MCP] {cfg.id} 连接失败，{backoff}s 后重试: {exc}")
                await asyncio.sleep(backoff)
                backoff = min(backoff * 2, 60)
```

**发现与热更新**：`_publish_tools` 调用 `session.list_tools()`，把每个 `mcp.types.Tool` 转成 `ToolDefinition`（`canonical_name = f"mcp.{cfg.id}.{tool.name}"`，`source_id = f"mcp:{cfg.id}"`，`build_tool` 直接用 `langchain_mcp_adapters.tools.convert_mcp_tool_to_langchain_tool(session, tool)`），调用 `tool_registry.publish(source_id=f"mcp:{cfg.id}", definitions=...)`。MCP 协议原生支持 `notifications/tools/list_changed`，`ClientSession` 收到通知时的回调里重新跑一次 `_publish_tools`，天然复用同一条热更新路径，不需要像 Skill 那样另外接文件 watcher。

**断线处理**：`_watch_disconnect` 检测到连接断开后，立即 `tool_registry.publish(source_id=f"mcp:{cfg.id}", definitions=[])`——把该 Server 的工具从快照里摘掉，而不是留着一份"看起来存在、实际调用必超时"的死工具让模型去踩。断线重连成功后重新发布，`registry_revision` 自然递增，符合 4.1 节"快照变更必须原子、可追溯"的设计。

**安全边界**：这是本节唯一需要额外强调的点——MCP Server 一旦连上，工具背后是**远程任意代码执行能力**，风险等级高于 Skill（Skill 脚本还在本地 `SandboxProvider` 受限执行）和前端工具（前端工具的执行结果始终经过 `ConnectionManager` 回到浏览器侧执行，不在服务端跑代码）。因此：
- `MCP_SERVERS` 只能通过部署配置（环境变量/配置文件）设置，**不接受运行时或前端请求动态添加新 Server**——这是它和"前端 `tool_list` 每条消息都能变"的本质区别，也是 4.3 节冲突策略里 `mcp` 优先级高于 `frontend` 的原因：MCP 是运维显式信任的来源，前端输入不是。
- `ToolPermissionStore` 的 `scope` 列（[tool_permission_store.py:10-11](../src/storage/tool_permission_store.py)）用 `scope=f"mcp:{cfg.id}"` 单独控制某个 MCP Server 的工具是否对某用户可用，不复用 `default` scope，避免一次性放开"所有 MCP 工具"。
- MCP 工具的执行仍然走 `GuardrailMiddleware`/`ToolAuditMiddleware` 这条既有链路（因为它们最终也是 LangGraph `ToolNode` 里的一个 `BaseTool`），不需要新的审计通道，但排障时要注意：失败原因可能来自远程 Server（网络、Server 内部报错），不是本地代码 bug，`ToolAuditMiddleware` 记录时应该把 `source_type=mcp` 带上，方便一眼区分。

## 五、Skill 热重载：唯一值得优先做的动态加载

### 5.1 触发

`watchfiles`（已确认在依赖树里——`uvicorn[standard]` 的 extras 带了它用于 `--reload`，`pip show watchfiles` 可验证已安装，不需要新增外部依赖，只是把它从"uvicorn 专用"提升为项目代码也直接 import 使用）监听 `SKILLS_DIRS` 配置的每个根目录下 `*/SKILL.md`。300~800ms 按 Skill 目录防抖，合并同一目录的多次 `modify` 事件。

### 5.2 候选构建

复用 `SkillLoader`——它已经是"全量扫描 → 单个失败跳过 → 返回新 `SkillRegistry`"的实现，热重载只需要：

```python
new_registry = SkillLoader(skill_dirs).load()   # 原样调用，零改动
new_definitions = SkillToolProvider(new_registry).discover()
await tool_registry.publish(source_id="skill", definitions=new_definitions)
```

`replace_source` 语义（`RegistrySnapshot.replace_source`）保证一个 Skill 被删除时，新快照里不会残留旧定义——不是"只增量追加"。

### 5.3 校验（发布前，不产生副作用）

- `model_name` 与其它已发布来源（`builtin`/`subagent`）冲突 → 拒绝整批发布，保留旧快照，记 error。
- `SkillDefinition.category` 不在 `SkillCategory` 枚举内 → `SkillLoader` 已经在解析阶段做了回退处理（[skill_loader.py:101-108](../src/agent_core/skills/skill_loader.py)），不需要重复校验。
- `required_secrets` 引用了不存在的密钥名 → 记 warning，不阻断发布（现有 `SkillToolFactory` 在真正执行时才会因为缺 secret 报错，这个信号留到执行时更准确，发布阶段做静态阻断反而可能因为密钥尚未配置就误杀一个本来该上线的 Skill）。
- **不做"脚本沙箱试跑"这类动态探测**——GPT 原方案里的"Executor 尝试初始化但不执行真实业务"对 Skill 脚本没有对应的轻量实现方式（`SkillToolFactory` 的执行路径本身就需要真正拉起 Sandbox），加上去成本远高于收益，跳过。

### 5.4 发布与失败处理

`publish()` 失败（`_validate` 抛异常）时旧快照原样保留，新版本状态记为 rejected 写日志；不影响在途请求——**在途请求这一点在当前架构下自动成立**，因为 `build_lead_agent()` 本来就是每次请求现造 Agent（[lead_agent.py:27-29 模块文档](../src/agent_core/agents/lead_agent.py) 已经解释过这个设计），不存在"一个长期存活的 Agent 实例持有旧工具引用"的问题，热重载只需要保证**下一次** `build_lead_agent()` 调用时 `skill_manager`/`tool_registry` 已经是新状态即可，不需要 GPT 方案里"在途请求继续持有旧快照直到结束"那一整套引用计数和 drain timeout 机制。

### 5.5 回滚

进程内保留最近 5 个 revision 的 `RegistrySnapshot`（内存态即可，单进程不需要落库），提供一个内部管理接口 `POST /admin/tool-registry/rollback?to_revision=N`（需要和现有管理接口的鉴权方式对齐，不在本文档展开）。

## 六、权限设计的增量修改

不新建权限体系，在现有两张表基础上做两处收紧：

1. **利用已预留的 `scope` 列**（[tool_permission_store.py:10-11](../src/storage/tool_permission_store.py) 注释已经写"预留用于未来按会话/角色等更细粒度授权"）：把 `source_type` 作为 `scope` 的一种取值传入，例如 `scope="frontend"` 单独控制"是否允许该用户使用前端自定义工具"，不需要改表结构。
2. **`resolve_tools` 解析阶段的裁剪结果写审计**：`RejectedTool` 列表随 `registry_revision` 一起记日志，回答"这个工具为什么模型看不到"不需要再去翻两张表手动核对。

不引入独立的"高风险工具人工审批"机制——当前工具集里没有对应现实场景（沙箱工具本身已经在受限 Sandbox 内执行，`sandbox_tool.py` 模块文档已说明其安全边界），加这一层是在为不存在的风险设计。

## 八、测试方案（按项目实际规模收敛）

**单元测试**：
- `model_name` 冲突时 `_merge` 按 `source_type` 优先级丢弃低优先级定义，并产生 warning（覆盖 4.3 节修复点）。
- `publish()` 校验失败时 `current_snapshot()` 保持不变。
- `replace_source` 删除一个 Skill 后，新快照里该 Skill 的 `canonical_name` 完全消失（不是残留)。
- `resolve_tools` 对 `enabled=false` 的定义直接跳过，不进入 Guardrail 校验（省一次不必要的 DB 查询）。
- Guardrail 拒绝的工具出现在 `rejected` 而不是 `tools` 里。

**并发测试**：
- 两次并发 `publish()` 串行执行（`_write_lock` 生效），最终 revision 正确递增、不丢更新。
- 大量并发 `current_snapshot()` 读取期间发生一次 `publish()`，所有读取者要么拿到旧快照要么拿到新快照，不出现半写状态（`frozen=True` dataclass + 单次引用替换即可保证，理论上不需要专门测试并发安全性，但值得写一个回归测试防止未来有人在 `publish` 里引入原地 mutate）。

**故障测试**：
- Skill 目录下某个 `SKILL.md` frontmatter 写坏（`SkillLoader` 已有容错，验证热重载路径下这个容错依然生效，不会因为一个坏文件导致整批候选发布失败）。
- 连续快速保存同一个 `SKILL.md` 5 次，验证只触发 1 次实际 reload（防抖生效）。
- MCP Server 连接中途断开：验证对应 `source_id` 的工具从快照里被摘掉（发布空列表），而不是留着调用必超时的死工具；重连成功后重新出现，`registry_revision` 递增。
- MCP Server 发送 `notifications/tools/list_changed`：验证只重新拉取并发布该 Server 的工具，不影响其它来源。
- `MCP_SERVERS` 配置为空（默认值）：验证 `MCPToolProvider.discover()` 返回空列表，其余三类来源和现有行为完全一致（回归测试，确保"兼容 MCP"不会在未配置时改变任何现有行为）。

不需要 GPT 原方案里"PostgreSQL/Redis 短暂不可用""多实例部分加载失败"这类测试——当前单进程部署下不存在对应场景。

## 九、实现落地记录：与本文档设计的实际偏差

Phase 1a/1b/2 已经按本文档实现（`agent_core/tools/registry/` 包 + `main.py`/`lead_agent.py`/`chat_pipeline.py`/`chat_ws.py` 接入），过程中发现几处设计阶段没预料到的细节，记录在这里，避免后续读这份文档的人以为代码和文字完全一一对应：

1. **`SkillToolFactory._invoke` 内部的 Guardrail 调用没有删除**，与 1.2 节草稿最初的判断相反。核实后发现 `web-researcher` subagent profile 会把 `web_search` 分类的 Skill 工具直接交给 `sub_agent_factory.run_subagent()` 执行，那条路径**不挂任何中间件**（`GuardrailMiddleware` 不在场），`SkillToolFactory` 内部这次校验是这条路径唯一的权限防线，删掉是真实的安全回退，不是无害去重。1.2 节正文已经同步更正。
2. **MCP 用轮询代替 `notifications/tools/list_changed` 推送**：技术选型定下来后（`langchain-mcp-adapters` 的 `MultiServerMCPClient`），发现它的 `get_tools()` 本身"每次调用都现开一个新 session"，没有对外暴露订阅 `list_changed` 通知的钩子；持有一个长期存活的 `ClientSession` 去手动处理该通知，工程量和收益不成正比。改为 `MCPConnectionManager` 按 `MCP_POLL_INTERVAL_SECONDS` 周期轮询 `get_tools()`，同时复用这次调用做可达性探测（失败即摘除该 Server 的工具、指数退避重连）。用户可感知的差异是：MCP Server 侧新增/删除工具后，最长要等一个轮询周期（默认 60s）才会体现在这边，不是准实时推送。
3. **`SkillToolProvider.discover()` 增加了 `registry` 覆盖参数**：`SkillHotReloader.reload_once()` 需要先用新扫描出的 `SkillRegistry` 试算 `ToolDefinition` 并试发布，只有 `ToolRegistry.publish()` 真正成功后才能把 `SkillManager.registry` 切换过去——如果反过来（先切 `SkillManager.registry` 再发布），一旦发布因为命名冲突被拒绝，就会出现"`ToolRegistry` 保留了旧状态，但 `SkillManager` 已经换到了被拒绝的新状态"这种两处状态互相矛盾的情况。加一个可选的 `registry` 参数就能让 `discover()` 在"还没正式切换"的阶段读到候选状态，不需要为热重载单独另写一套发现逻辑。
4. **没有实现 5.5 节提到的 `POST /admin/tool-registry/rollback` HTTP 接口**：`ToolRegistry.rollback(to_revision)` 方法本身已经实现（进程内保留最近 5 次发布前的快照），但当前代码库里没有任何"管理员接口"的鉴权模式可以依附（`skill_router.py` 这类现有路由完全没有鉴权层），5.5 节当时也写了"需要和现有管理接口的鉴权方式对齐，不在本文档展开"——维持这个决定，回滚目前只能通过直接调用 `get_tool_registry().rollback(...)`（比如在一个临时脚本/REPL 里）触发，等项目有了统一的管理接口鉴权方案再补 HTTP 包装层。
5. **`build_lead_agent()` 从同步函数改成了 `async def`，返回值从单个 `agent` 变成 `(agent, registry_revision)` 二元组**：因为 `resolve_tools()` 内部要 `await` Guardrail 校验。两个调用点（`chat_pipeline.py` 的 `run_chat_turn`/`run_regenerate_turn`）都已经是 `async def`，改动是纯粹的信号穿透，没有引入新的并发复杂度；但这是一处不向后兼容的公开签名变化，如果后续还有别的地方直接调用 `build_lead_agent()`（目前 grep 确认只有这两处），需要同步改造。

## 十、一句话版结论

现有"构建时列表拼接"方案在权限校验上其实比想象中统一（`GuardrailMiddleware` 已覆盖全部工具），真正缺的是**元数据的统一视图**、**Skill 免重启更新**，以及**一个能接真实 MCP Server 而不用改动核心链路的一等来源**。用一层薄的 `ToolDefinition`/`Provider` 适配现有四个来源加上新增的 `MCPToolProvider`、不重写任何一个已经稳定的执行工厂，配合进程内 copy-on-write 快照做 Skill 热重载，投入产出比最高；GPT 方案里面向多实例注册表同步、人工审批工作流的部分留作 Phase 3，等对应的真实需求出现（真的要横向扩容）再启动，现在做只是给一个单进程单体应用增加不必要的分布式系统复杂度。
