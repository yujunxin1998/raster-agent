# 典型测试用例

持续累积的活文档：**任何触及 Agent 调用链路的改动**（工具路由、委派/分发机制、
技能挂载方式、中间件顺序等）完成后，都要在对应分节里补上能触发这条链路的典型
自然语言 query，方便下次改动/回归时直接复用，不用每次重新现想测试场景。

新增分节时请遵循已有格式：每条 query 用真实自然语言（不是伪代码/参数），并注明
"验证什么"（期望触发哪个工具、期望什么可观察行为）。

推荐验证方式：用 `run_chat_turn()` 直接探针跑（绕开 WS/uvicorn，参考
`agent_core/agents/chat_pipeline.py` 的用法），逐个检查 yield 出来的
`tool_call`/`skill_call` 事件里的 `tool_name`，而不是只看最终回复文本——最终回复
即使内容合理，也可能是模型换了个错误的工具路径凑出来的。

---

## 通用分发 `task()` 工具（web_search，`agent_core/agents/delegation_tools.py`）

- "今天上证指数收盘涨跌幅是多少？"
  验证：出现 `tool_call` 事件，`tool_name == "task"`，参数里
  `subagent_type == "web-researcher"`；不应该出现任何 `delegate_to_xxx` 名字的
  工具（那套已经删除）。
- "帮我查一下上海各区县的 GeoJSON 边界数据"
  验证：先触发一次 `task(subagent_type="web-researcher", ...)` 拿到链接/数据，
  而不是模型凭记忆编造 URL 直接调用地图工具。
- "5+3等于几" / "你好，介绍一下你自己"
  验证：**不应该**触发 `task` 工具——纯闲聊/简单计算应该被 Lead Agent 自己直接
  回答，不该误路由到联网搜索。
- "帮我对比分析 AWS、Azure、GCP、阿里云和 Oracle Cloud 这 5 个云平台，我需要
  进行所有维度的分析，为了写一个总结报告"
  验证：`subagent_system.md` 新增的"并行拆分原则"生效——预期看到**同一轮响应
  里 5 次并行的** `task(subagent_type="web-researcher", ...)` 调用，每次的
  `task` 参数聚焦单个平台，而不是把多个平台揉进 1-2 个更宽泛的搜索描述里
  （本轮修复前的真实故障现象：5 个平台只触发了 2 次 `task` 调用）。这条同时
  会撞上 `recent_tool_calls` 并行写入 state 的场景，建议跟
  `LoopDetectionMiddleware`/`PipelineState` 的并行工具调用回归一起验证。
  同时可顺带验证下面"轻量任务规划"一节——这句话本身也是触发 `update_plan`
  的典型场景。
- 承接上一条：把 `SUBAGENT_MAX_CONCURRENCY` 调小（比如 2），再问同一句"对比
  5 个云平台"
  验证：`build_task_tool()` 内部的 `asyncio.Semaphore` 生效——探针数一下同一
  时刻真正在执行（而不是已经发起）的 `run_subagent` 调用数，不应该超过配置值；
  5 个 `task` 调用应该分批执行完，不应该报任何"并发过多"之类的错误（超限是
  排队等待，不是拒绝）。
- 把 `SUBAGENT_TIMEOUT_SECONDS` 调小（比如 1），问一句会触发 `task` 的问题
  验证：`run_subagent()` 应该在超时后返回"执行超时（超过 N 秒），已中止"这类
  说明文本给模型（`sub_agent_factory.py::_TIMEOUT_TEMPLATE`），而不是让整轮
  对话卡死不响应。

## 轻量任务规划（`agent_core/tools/plan_tools.py::update_plan` + `agent_core/agents/plan_middleware.py::PlanContextMiddleware`）

> 模型自愿调用的"计划草稿纸"，不是强制流程；`update_plan` 每次调用都是完整
> 覆盖，不是增量修改。只挂在 Lead Agent 上，`web-researcher` 等 subagent 没有
> 这个工具。`update_plan` 是普通 `@tool`，天然走通用 `tool_call`/`tool_response`
> 事件（跟 `task` 走同一条链路，不是独立事件类型），`ToolMessage` 正文里带
> `<plan>{json}</plan>` 标签供前端解析渲染成清单 UI，跟
> `save_output_file` 的 `<image>` 标签是同一套既有约定
> （`sandbox_tool.py`/`useChatStore.js::_extractImageBlocks`）。

- "帮我对比分析 AWS、Azure、GCP、阿里云和 Oracle Cloud 这 5 个云平台，我需要
  进行所有维度的分析，为了写一个总结报告"（跟上面"通用分发"一节共用同一句）
  验证：第一次响应里应该先出现一次 `update_plan` 调用（`tool_name ==
  "update_plan"`），`args.plan` 里大致能看到按平台拆分的步骤；之后每次模型
  调用（探针打印实际发给模型的 `system_prompt`/`messages`）都应该能看到
  `<current_plan>...</current_plan>` 块，内容随后续 `update_plan` 调用更新。
- 上一条场景执行到一半时，人为在某次 `web-researcher` 子任务里让搜索结果
  明显偏离预期（比如让 mock 返回"该平台已停止服务"这类反常信息）
  验证：模型应该有较大概率再调用一次 `update_plan` 调整计划（比如跳过/替换
  这一步），而不是对着不合理的信息硬着头皮走完原计划——这是"建议性调整"这一
  版本的核心能力点，允许调整但不保证一定发生（没有强制的评估中间件），观察
  多次运行的整体倾向即可，不用要求每次都触发。
- 一句简单闲聊/无需拆解的问题（比如"你好"）
  验证：**不应该**触发 `update_plan`——简单任务不需要建计划，也不应该出现
  `<current_plan>` 块（`request.state` 里没有 `plan` key 或为空列表时，
  `PlanContextMiddleware` 应该是纯粹的 no-op，不改写 `system_prompt`）。
- 承接第一条场景：模型第一次调用 `update_plan` 之后，检查 WS 层实际推给前端的
  `tool_response` 事件（`chat_pipeline.py::_handle_tool_message` 产出，探针打
  `run_chat_turn()` 的 yield 结果即可，不用起真的前端）
  验证：`content` 字段里应该同时包含人类可读的 `计划已更新：\n- [pending] ...`
  文本和机器可解析的 `<plan>[{"content": "...", "status": "..."}, ...]</plan>`
  标签（`re.search(r"<plan>(.*)</plan>", content, re.DOTALL)` 能提取出合法
  JSON）；再调用一次 `update_plan`（比如把某一步标成 completed），应该再触发
  一次同名 `tool_response` 事件，`<plan>` 标签内容随之更新——前端拿这个事件流
  就能做出"实时刷新的执行清单"效果，不需要额外轮询接口。
  这一步"前端要不要真的解析渲染"不在这个仓库验证范围内（`diit-agent-web` 是
  独立仓库），这里只确认后端产出的事件/标签内容本身正确、稳定。

## 知识库检索 Tool（`agent_core/tools/knowledge_search_tool.py`，指导技能
`skills/core/knowledge-base-answering/`）

> `docs/Skill与Tool完全解耦重构设计.md` 迁移后：`search_knowledge_base` 不再是
> "有 `parameters` 的 Skill"，而是独立挂在 Lead Agent 工具集上的 `@tool` 函数，
> 原 Skill 目录改名为 `knowledge-base-answering`、改造成纯指令型 WORKFLOW 技能
> （只负责教模型"什么时候查、怎么标注引用"，`required_tools: [search_knowledge_base]`）。

- "帮我查一下知识库里关于地质灾害应急管理的规定"
  验证：出现 `tool_call` 事件，`tool_name == "search_knowledge_base"`，是一次
  直接的工具调用（不再经过任何 Skill 脚本子进程）。
  当前开发环境 `RAG_API_URL` 未配置，预期表现是工具返回"知识库检索服务当前
  不可用"一类的说明文字，不是让整轮对话崩溃——这是需要确认的容错路径。
- 回答里如果确实检索到了内容，逐句检查是否用 `[n]` 格式标注来源，正文结束后
  是否有 `<ref_json>{"sources":[...]}}</ref_json>` 结尾块——这段提示现在由
  `RAGService.format_knowledge_chunks()` 直接拼进工具返回值（不再经 Skill 脚本
  的 `__metadata__` 中转），`knowledge-base-answering` SKILL.md 正文里也重复
  教了一遍同样的格式，两处应该一致。

## 数据库查询 Tool（`agent_core/tools/database_query_tool.py`，指导技能
`skills/core/database-analysis/`）

- 配置 `datasource_id` 后问："帮我看下上个月的订单总金额"
  验证两件事：① `DatasourceRoutingMiddleware` 硬路由仍然生效（它检查的是字面量
  工具名 `"query_database"`，跟 Skill/Tool 拆分无关）——如果模型第一次响应没有
  调用 `query_database`，应该看到中间件注入纠正提示并强制重试一次；② 当前开发
  环境 `DB_QUERY_API_URL` 大概率不可达，预期返回"数据库查询失败"文本而不是
  抛异常。
- **不配置** `datasource_id` 直接问同样的问题
  验证：模型应该直接告知"未配置数据源"，不强制重试（`DatasourceRoutingMiddleware`
  在没有 `datasource_id` 时应该整段跳过校验）。

## 沙箱工具（`agent_core/tools/sandbox_tool.py`：write_file/read_file/run_python/run_command）

- "帮我在沙箱里写一个 Python 脚本 quicksort.py 实现快速排序，先故意留一个下标
  越界的 bug，运行看报错，然后自己定位并修复，最后跑通并给我看测试输出。"
  验证：完整的"写→跑→报错→改→再跑"链路，每个 `write_file`/`run_python` 调用都
  应该先出现一次 `pending: true` 的占位事件（工具名已知、参数还没流完），再
  出现一次带完整参数的正式事件——两者 `request_id` 相同。
- 连续对同一条命令重试三次以上（故意制造死循环场景）
  验证：`LoopDetectionMiddleware` 在第 3 次完全相同的调用时应该短路，返回
  "检测到已连续 N 次以相同参数调用工具"的提示，而不是无限重试。
- 上述 quicksort 场景完整跑完大约需要 15-20 个 recursion 单位（3 个单位/轮 ×
  好几轮 write/run），如果改了 `lead_agent.py` 的 `_DEFAULT_RECURSION_LIMIT`/
  `_THINKING_RECURSION_LIMIT`，拿这个场景回归一下，确认没有在合理轮数内被
  `GRAPH_RECURSION_LIMIT` 打断。
- "用 run_python 跑一段代码，打印 0 到 199 一共 200 行数字"（触发超过
  `SANDBOX_INLINE_OUTPUT_MAX_LINES` 默认值 50 行的长输出）
  验证：`tool_response` 事件里的内容不应该是完整 200 行，应该是"共 200 行，
  超过 50 行预览上限，仅展示头尾...完整内容已保存到 tool_output/xxxxx_stdout.log"
  这种头尾预览 + 落盘提示；随后追问"帮我看看 xxx 行附近的完整输出"应该触发
  `read_file(path="tool_output/xxxxx_stdout.log")` 读到完整内容。
- "用 run_python 打印 10 行内容"（低于 50 行阈值）
  验证：应该原样内联返回，**不应该**出现 `tool_output/` 落盘路径，确认没有对
  短输出场景引入不必要的磁盘 IO。

## WebSocket 流式事件（`agent_core/agents/chat_pipeline.py` + `streaming_model_middleware.py`）

- 任意会触发工具调用、且工具参数较长的问题（比如上面的 quicksort 场景，
  `write_file` 的 `content` 参数经常有几百到一千多字符）
  验证：`tool_call`/`skill_call` 事件不应该出现 `tool_name` 为空字符串或
  `request_id` 为 `None` 的野事件——这是"任务卡在写文件这一步不动"那个 bug 的
  根因，修复后应该每个真实工具调用只对应一次 pending + 一次完整事件，不多不少。

## 会话标题生成（`agent_core/middlewares/title.py`）

- 任意**第一轮就会触发工具调用**的问题（比如"今天上证指数收盘涨跌幅是多少？"
  这种会走 `task` 工具的、或者会触发 `search_knowledge_base`/`query_database`
  的）
  验证：几秒后 `conversations` 表里的 `title` 字段应该从默认的"新对话"变成
  真实生成的标题，不能停留在"新对话"不动——`TitleMiddleware` 曾经用
  `len(messages) > 2` 判断"是不是第一轮"，只要第一轮里有任何工具调用（哪怕只
  调用一次），消息数就会超过 2，导致标题永远生成不出来；现在改成数
  `HumanMessage` 条数，第一轮无论中间调用几次工具都应该正常触发。
- 一句纯闲聊/不触发任何工具的问题（比如"你好，介绍一下你自己"）
  验证：同样应该正常生成标题——这条用来确认"改成数 HumanMessage"没有连带破坏
  最简单的无工具调用场景。
- 同一个 conversation_id 下追问第二句
  验证：标题不应该被二次覆盖/重新生成（`TitleMiddleware` 只在第一轮触发一次）。

  路径——如果翻译失败，预期报错信息类似"No such file or directory"，能在

  验证：stdin 参数通过会话工作区内的 `0600` 一次性输入文件传入容器，脚本正常

- 仅在开发者本地把 `CURRENT_ENV=development`、`SANDBOX_PROVIDER=local`
  验证：`write_file`/`run_python`/`run_command` 可以用于本地测试；任何线上环境配置
  Local 都必须启动失败。

## 产物下载链接（`save_output_file` 工具 + `GET /conversations/{id}/outputs/{path}`）

- "帮我把刚才的分析结果写成一份 markdown 报告，保存成可以下载的文件"
  验证：应该触发 `tool_call`，`tool_name == "save_output_file"`（不是
  `write_file`——两者的区别是落地目录不同，`write_file` 写的是中间过程文件，
  `save_output_file` 才会生成下载链接）；工具返回文本里应该出现
  `/conversations/{conversation_id}/outputs/{文件名}` 格式的链接，配了
  `PUBLIC_BASE_URL` 时链接应该带上这个前缀（绝对 URL），没配时是相对路径。
- 在前端（和后端不同源部署，比如本地 `localhost:5173` 前端 + `localhost:8080`
  后端这种典型开发环境）里点开上一条生成的下载链接
  验证：**不配置** `PUBLIC_BASE_URL` 时点击会打到前端 SPA 自己的地址而不是
  后端（前端框架可能报"did you mean to visit .../outputs/... instead?"这类
  提示，或者直接 404/空白页）——这是相对路径在跨源部署下的已知问题；
  配置 `PUBLIC_BASE_URL=http://localhost:8080`（改成实际后端地址）后重新触发
  一次，点击链接应该能正确打到后端下载接口。
- 拿下载链接直接 `curl` 一下（带上正确的 `user_id` 查询参数）
  验证：能拿到 200 和文件原始内容；不带 `user_id` 或传一个不属于该会话的
  `user_id` 时应该拿到 404（owner 校验生效）；在 `file_path` 里塞
  `../../` 之类的路径穿越尝试应该被拒绝（400 或 404，不应该读到 workspace/
  目录之外的文件）。

## 记忆 staleness 定期复核（`agent_core/memory/memory_staleness_reviewer.py`）

> Memory v2 起改为直接扫描 `UserMemoryFactStore`（PostgreSQL 规范化主存），
> 不再调 ES；归档后由 `FactProjector` 异步把变化同步进 ES 投影，不是
> `MemoryStalenessReviewer` 自己操作 ES。

- 手工在 `user_memory_fact` 里插入一条 `importance=1`、`access_count=0`、
  `created_at` 是 100 天前、`status=active` 的记录，调用
  `MemoryStalenessReviewer.run_once()`（或等 `MAINTENANCE_INTERVAL_HOURS`
  周期到）
  验证：`status` 从 `active` 变成 `archived`；通过 `GET /memories/` 管理接口
  应该还能看到这条记忆（是归档不是物理删除），但正常的 `search()` 召回里
  不应该再出现它——同时确认 ES 投影里对应文档也被 `FactProjector` 删除
  （`memory_outbox` 表里应该能看到一条已处理的 `fact_status_changed` 记录）。
- 手工插入一条 `expires_at` 已经过去、但 `importance`/`access_count` 都不满足
  低价值条件的记录
  验证：同样应该被归档为 `archived`——过期判定和低价值判定是"满足任一即可"
  的关系，不是必须同时满足。

- 在最后一条 assistant 消息上点"重新生成"图标
  验证：这条消息应该从视图上消失，替换成一个新的流式生成气泡；生成完成
  后刷新会话历史，应该只看到一条 assistant 回复（旧的那条已被
  `delete_last_assistant_message` 清理），不会同时存在新旧两条。
- 对一条不是"最后一条"的历史 assistant 消息（前面还有更晚的对话）
  验证：这条消息的反馈按钮行不应该出现"重新生成"图标（只有真正最后一条
  assistant 消息才有），赞/踩按钮不受影响、正常可点。
- 重新生成过程中，立刻再点一次"重新生成"或者在输入框发一条新消息
  验证：都应该被挡住（跟"同一会话不能连续发两轮"是同一条规则），要等
  这一轮 `done` 事件到达之后才能再次触发。
- 一个只发过一句话、AI 还没回复完（或者回复失败、从没成功落库过 assistant
  记录）的全新会话，理论上不会出现这个场景（反馈按钮只在 `status===done`
  的 assistant 消息上渲染），可以跳过手工验证，但如果直接拿 WS 协议发一条
  `action:"regenerate"` 给一个没有任何用户发言的空会话
  验证：后端应该静默返回 `done`（不落库、不报错），对应
  `chat_pipeline.py::run_regenerate_turn` 里"会话尚无用户发言"的兜底分支。

## Skill 与 Tool 完全解耦重构：自动预路由 + 统一 `SkillMiddleware`（`agent_core/skills/`、`agent_core/agents/skill_middleware.py`，见 `docs/Skill与Tool完全解耦重构设计.md`）

> 这是对上一版"Skill 注入重构"（`docs/Skill注入与Load-Skill重构设计.md`，
> 上面的历史小节已过时，仅供追溯背景）的进一步收敛，核心变化三点：
> 1. **自动预路由**：`activation: required` 或用户/API 显式指定的技能，在
>    **本轮首次模型调用前**就由 `SkillMiddleware` 直接把正文注入
>    `system_prompt`，不再依赖模型主动调用 `load_skill`（`skill_router.py`
>    的规则匹配：显式指定/`required` → `forced`；其余 `automatic` → 仍走
>    `<skill_catalog>` 目录 + 模型按需 `load_skill`）。
> 2. **不再有"参数化 Skill"**：`search_knowledge_base`/`query_database` 已
>    迁移成独立业务 Tool（见上面两个专门小节），`SkillKind`/`SkillToolFactory`
>    已删除，任何 Skill 现在都是"纯指令 + 参考资料"。
> 3. **Lead Agent 与 subagent 统一路径**：`web-researcher` 现在也显式挂载
>    `SkillMiddleware`（不再有"自包含 `load_skill` 兜底实现"这条第二路径），
>    两边用同一个中间件、同一份 `SkillActivationService`。

- "帮我把这组数据做成柱状图"（触发一个 `activation: automatic` 的工作流技能，
  如 `chart-visualization`）
  验证：`system_prompt` 里先出现 `<skill_catalog>` 目录，模型据此主动调用
  `load_skill(skill_name="chart-visualization")`；随后应该出现
  `run_command`/`run_python` 调用，命令行参数里的脚本路径应该是一个真实存在的
  绝对路径（不是 `/mnt/skills/...`）——验证 `SkillPathRewriter` 仍然生效。
- 把某个技能的 SKILL.md frontmatter 加一行 `activation:\n  mode: required`
  （或用测试专用技能验证），问一句完全不相关的闲聊，比如"你好"
  验证：**第一次**模型调用的 `system_prompt` 里就应该能看到这个技能的完整正文
  （不是只有目录条目），模型**不需要**调用 `load_skill`——这是本轮重构要验证
  的核心点，之前的设计下这个场景完全依赖模型自己判断"要不要查目录"。
- 同一会话里连续问两次都会触发同一个 `required` 技能的问题
  验证：第二次模型调用不应该看到该技能正文被重复完整注入两遍——`activated_skills`
  状态应该记录"已激活"，第二次只是延续同一份上下文，不是重新拼一遍。
- 在 `user_tool_permissions` 表里单独禁用某个用户的某个技能（不是禁用
  `load_skill` 整体），用这个 `user_id` 触发同一个技能
  验证：无论这个技能是 `forced`（首次调用前自动激活）还是 `catalog_candidates`
  （模型主动 `load_skill`），都应该被拒绝且不影响该用户加载其它技能——Guardrail
  校验按具体 `skill_name`，不是恒定的 `"load_skill"`。
- "帮我调用一个叫 xxx-not-exist 的技能"（诱导模型传一个不存在的 `skill_name`）
  验证：`load_skill` 应该返回"未找到"文案，不应该抛异常中断整轮对话。
- 需要联网搜索的问题（比如"帮我研究一下 xxx 最新进展"），且 `web_search` 分类下
  存在工作流技能（如 `deep-research`）
  验证：`task(subagent_type="web-researcher", ...)` 内部应该能看到
  `load_skill(skill_name="deep-research")` 正常工作——这条路径现在也挂了
  `SkillMiddleware`，跟 Lead Agent 走同一套激活逻辑，行为应该完全一致（不再是
  两套独立实现各自维护）。
- 修改一个工作流技能的 `SKILL.md`（比如改某个技能的 `description`）后
  **不重启进程**，隔几秒再问一句触发它的问题
  验证：新 `description` 应该出现在下一轮的 `<skill_catalog>` 里；同时确认
  `GET /tools`（或直接看 `ToolRegistry.current_snapshot().revision`）没有因为
  这次 Skill 改动而变化——Skill 热重载已经不再触碰 `ToolRegistry`。
- 触发一次 `read_skill_resource`（模型在 `load_skill` 拿到资源索引后按路径读取
  某个 reference/脚本文件）
  验证：正常路径返回文件内容；诱导传一个 `../../` 或绝对路径的 `resource_path`，
  验证返回"拒绝"文案而不是读到技能目录外的文件。

## 决策顺序：先 skill 后 tool 再 plan（`agent_core/prompts/system/lead_agent/role.md`）

> 纯提示词层面的显式排序，不引入代码强制分支——跟 `plan_system.md` 同一性质，
> 不保证模型每次都严格照做，只是把之前分散在 `skill_system.md`/
> `subagent_system.md`/`plan_system.md` 三个模块里、彼此不互相引用的隐式顺序，
> 收敛成 `role.md` 开头一段显式的"先看技能→再看工具→再判断要不要建计划"说明。
> `activation: required`/显式指定的技能已经由 `SkillMiddleware` 强制注入，不
> 依赖模型自己判断，这里验证的是 `catalog_candidates`（`automatic`）技能这条
> 仍然需要模型自己决策的路径。

- "帮我分析一下这份 Excel 销售数据"（先上传一个 xlsx 文件，命中
  `activation: automatic` 的 `data-analysis` 工作流技能）
  验证：模型应该先调用 `load_skill(skill_name="data-analysis")`，再调用
  `run_python`/`run_command` 之类的工具，不应该跳过技能直接自己现编排一套文件
  读取/分析流程。
- "对比 OpenAI、Claude、Gemini 在 Agent 开发场景中的能力、工具调用、上下文窗口、
  价格和生态，并给出创业团队的选型建议"（`<skill_catalog>` 里没有匹配的技能，
  但涉及多个独立对象 + 多个维度）
  验证：第一步（技能）应该直接跳过（目录里没有相关技能，不应该出现无意义的
  `load_skill` 尝试）；第二步应该看到按对象拆分的多个并行 `task` 调用；第三步
  应该看到 `update_plan` 被调用，`<current_plan>` 在后续模型调用里出现——三步
  在同一次真实对话里都验证到，是本节存在的核心目的。
- 纯闲聊，比如"你好，你能做什么"
  验证：三步都不应该触发任何工具调用（`load_skill`/`task`/`update_plan` 均不
  出现），直接文本回复——确认这段决策顺序说明不会把简单任务过度复杂化。
