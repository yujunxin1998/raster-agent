# 模型服务接入适配手册

本手册说明 `raster-agent` 当前的模型接入架构、每个 provider 已经做了哪些适配，
以及接入一个新模型服务时需要改动哪些文件、要注意哪些坑。目标读者：需要新增
一个 provider（如换一家 OpenAI 兼容网关、接入 Claude/Gemini 官方 API 等）的
开发者。

## 1. 现有设计：一个入口 + 按 provider 分支

所有模型调用都必须经过统一入口 [`create_chat_model()`](../src/agent_core/model/model_factory.py)
（对外导出自 `src/agent_core/model/__init__.py`），禁止在业务代码里直接
`ChatOpenAI(...)`/`init_chat_model(...)`。这是唯一的组装点，好处是：

- 供应商特有的坑（字段丢失、多轮续接、思考模式开关）全部收敛在
  `model_factory.py` + `patched_*.py` 里，业务代码（中间件、Agent、工具）
  只管调 `create_chat_model(...)`，不需要知道 provider 差异。
- 不缓存模型实例。原 `diit-agent-server` 项目的 `LLMFactory` 按
  `(purpose, kwargs)` 缓存单例；本项目认为模型实例构造成本低（纯 Python
  对象组装，不发起网络请求），现造一个的开销可以忽略，而缓存带来的"同一个
  实例被多处意外共享 callbacks/状态"的心智负担更值得避免。

### 1.1 调用方（谁在用 `create_chat_model`）

| 调用方 | 用途 | 关键参数 |
|---|---|---|
| [`lead_agent.py`](../src/agent_core/agents/lead_agent.py) | 主对话模型 | `thinking_enabled` 来自请求 |
| [`sub_agent_factory.py`](../src/agent_core/agents/sub_agent_factory.py) | 委派子 Agent | 无覆盖，全部走默认配置 |
| [`memory_compressor.py`](../src/agent_core/memory/memory_compressor.py) | 会话历史压缩摘要 | 可能指定独立的 `MEMORY_COMPRESS_MODEL` |
| [`memory_extractor.py`](../src/agent_core/memory/memory_extractor.py) | 长期记忆提取 | 可能指定独立的 `MEMORY_EXTRACT_MODEL` |
| [`title.py`](../src/agent_core/middlewares/title.py) | 会话标题生成 | 独立、低成本的一次性调用 |
| [`database_tool.py`](../src/agent_core/tools/database_tool.py) | SQL 解读/图表元数据/结果解读 | `temperature`/`max_tokens`/`timeout` 覆盖 |

这些调用方都不关心 provider 是谁——新增一个 provider 时，**不需要改动
这些文件**，除非该 provider 需要传入新的专属参数（这种情况很少见，出现时
优先考虑做成 `**overrides` 透传而不是改调用签名）。

### 1.2 `create_chat_model()` 的分支逻辑

```
create_chat_model(model=None, provider=None, api_key=None, base_url=None,
                   thinking_enabled=False, **overrides)
    │
    ├─ resolved_* 参数缺省时回落到 settings（见 2.1）
    │
    ├─ provider == "deepseek"          → PatchedChatDeepSeek(...)
    ├─ provider in {"vllm","qwen"}     → PatchedChatOpenAI(...)   （chat_template_kwargs 开关思考模式）
    │  或 provider=="openai" 且模型名含 "qwen"
    │
    └─ 其余 provider                    → init_chat_model(...)     （LangChain 官方通用工厂）
```

`thinking_enabled` 是唯一跨 provider 的语义参数：不同 provider 表达"开启
深度思考"的方式完全不同（见第 3 节），`create_chat_model` 负责把这个统一
开关翻译成每个 provider 各自的请求格式，调用方不需要关心翻译细节。

## 2. 配置层：`settings.py`

### 2.1 字段与回退关系

```python
# 遗留字段（历史上只支持 DeepSeek 时留下的命名）
API_KEY / BASE_URL / DEFAULT_MODEL / PROVIDER

# DeerFlow 风格字段（OpenAI 兼容 / vLLM 场景优先读这组）
OPENAI_API_KEY / OPENAI_BASE_URL / OPENAI_MODEL / OPENAI_MODEL_THINKING
```

`API_KEY`/`BASE_URL`/`DEFAULT_MODEL` 的默认值会优先读 `OPENAI_*` 对应的环境
变量，读不到再退回旧变量名——所以 `TitleMiddleware`、`MemoryCompressor`
等只认 `settings.API_KEY`/`BASE_URL`/`PROVIDER` 的旧调用方，**不需要任何
代码改动**就能自动跟着 `.env` 里的 `OPENAI_*` 配置切换 provider。

`PROVIDER` 未显式设置时的默认值有一条隐式规则：`.env` 里配了
`OPENAI_BASE_URL` 就默认为 `"vllm"`，否则默认为 `"deepseek"`——新增
provider 时如果想复用这条自动判断逻辑，需要在 `settings.py` 里显式加分支，
不要指望它能自动识别第三个 provider。

### 2.2 新增 provider 需要碰 `settings.py` 的场景

- 新 provider 需要一个独立的 API Key/Base URL/Model 变量组（不想复用
  `OPENAI_*`）→ 按 `OPENAI_*` 那组的写法新增一组字段。
- 新 provider 有自己的"思考模型"或类似的专属开关字段（参考
  `OPENAI_MODEL_THINKING`）→ 新增对应字段，命名前缀保持与该 provider 一致。
- 不要复用别的 provider 的字段名存新 provider 的值（例如把 Claude 的 Key
  硬塞进 `OPENAI_API_KEY`）——这会让 `.env` 变得无法阅读，也会在同时启用
  多个 provider 时冲突。

同时记得在 [`.env.example`](../.env.example) 里补一段示例配置块，格式参考
现有的 `# OpenAI-compatible / vLLM models` 那段注释。

## 3. 已有 provider 的适配细节（新 provider 接入前必读）

理解现有两个 provider 已经踩过的坑，能帮你判断新 provider 是否会遇到同类
问题。

### 3.1 DeepSeek —— [`patched_deepseek.py`](../src/agent_core/model/patched_deepseek.py)

- 用的是供应商专用包 `langchain_deepseek.ChatDeepSeek`，**响应解析**天然
  认识 `reasoning_content` 字段（会自动放进 `additional_kwargs`），这一层
  不需要额外修。
- 但 LangChain 序列化**请求**负载时默认不会把上一轮 assistant 消息的
  `reasoning_content` 带回给 API；某些接口要求多轮对话里每条 assistant
  消息都携带 `reasoning_content` 才能维持推理连续性。`PatchedChatDeepSeek`
  重写 `_get_request_payload`，按位置把 `original_messages` 里的
  `additional_kwargs["reasoning_content"]` 回填进序列化后的请求 dict。
- `thinking_enabled` 的表达方式：`extra_body={"thinking": {"type": "enabled"/"disabled"}}`。
- 直连环境下用 `httpx.Client(trust_env=False)`，避免 shell 里的
  `ALL_PROXY`/`HTTP(S)_PROXY` 被 httpx 隐式拾取、把请求打到不可用的本地代理。

### 3.2 Qwen / vLLM —— [`patched_vllm.py`](../src/agent_core/model/patched_vllm.py)

- 用的是通用包 `langchain_openai.ChatOpenAI`（因为 vLLM 暴露的是 OpenAI
  兼容接口，没有专用 LangChain 包）。**这里有个非常容易踩的坑**：
  `ChatOpenAI` 的官方 docstring 明确写明它只解析标准 OpenAI 协议字段，
  第三方供应商（vLLM、OpenRouter 等）扩展的非标准字段——包括 vLLM 用来
  承载 Qwen3 思考内容的 `reasoning_content`——会在响应解析阶段被**直接
  丢弃**，不会出现在 `content` 或 `additional_kwargs` 里。
  - 症状：开启"深度思考"开关后模型正常工作，但前端收不到任何思考过程，
    像是开关没生效——实际上开关本身没问题（`chat_template_kwargs.
    enable_thinking` 确实发到了 vLLM），问题出在响应解析这一层。
  - 修复：`PatchedChatOpenAI` 重写 `_convert_chunk_to_generation_chunk`
    （流式）和 `_create_chat_result`（非流式），从 SDK 返回的原始
    `delta`/`message` dict 里把 `reasoning_content` 摘出来，写回
    `additional_kwargs["reasoning_content"]`——刻意用和 DeepSeek 分支
    相同的字段名，让下游 `chat_pipeline.py::_handle_ai_message`
    （见 3.3）不需要感知 provider 差异。
- `thinking_enabled` 的表达方式：`extra_body.chat_template_kwargs.
  enable_thinking = True/False`（vLLM 的 Qwen3 chat template 专属开关）。
- 支持"独立思考模型"：如果 `.env` 配了 `OPENAI_MODEL_THINKING` 且和
  `DEFAULT_MODEL` 不同（如 `qwen3` vs `qwen3-thinking`），开启思考时会
  直接切换到那个模型，而不是对同一个模型下发 `enable_thinking` 标志；
  没配置独立思考模型时，用 `enable_thinking` 标志切换同一个模型的行为。
- API Key 允许为空，为空时传 `"EMPTY"`（vLLM 本地部署通常不校验 Key，但
  `ChatOpenAI` 要求这个字段非空字符串）。

### 3.3 思考内容的下游消费：`chat_pipeline.py`

无论哪个 provider，思考内容最终都要流到前端的 WS `thinking` 事件。判断逻辑
在 [`chat_pipeline.py::_handle_ai_message`](../src/agent_core/agents/chat_pipeline.py)：

```python
if thinking:
    reasoning = message.additional_kwargs.get("reasoning_content", "")
    if reasoning:
        out.append({"type": "thinking", "content": reasoning})
    # 以及：content 是结构化 list 且包含 {"type": "thinking", "thinking": ...}
    # 的 Anthropic 风格思考块（预留给未来接入 Claude 系列 provider）
```

**这是接入新 provider 时最容易漏掉的一步**：如果新 provider 的思考内容
既不是 `additional_kwargs["reasoning_content"]`，也不是 Anthropic 风格的
结构化 `thinking` content block，必须在这里（或在新 provider 自己的
`patched_*.py` 里统一转换成上述两种格式之一）补一个分支，否则思考内容
会在这一步被静默吞掉——现象和 3.2 提到的完全一样："开关开着但前端看不到
思考过程"。

## 4. 接入新模型服务的标准步骤

以接入一个假设的 "Foo" 供应商（`PROVIDER=foo`）为例：

1. **确认协议兼容性**
   - 完全兼容 OpenAI Chat Completions 协议、且不需要任何非标准字段 →
     可以直接在 `model_factory.py` 里让它落到 `init_chat_model(model_provider="foo", ...)`
     或复用 `ChatOpenAI`，不需要新建 `patched_*.py`。
   - 有非标准响应字段（思考内容、扩展 usage 统计等）需要保留 → 需要一个
     `PatchedChatFoo` 子类，参考 `patched_vllm.py` 的做法：找到父类负责
     "把 SDK 原始 dict 转成 LangChain 消息对象"的方法（流式通常叫
     `_convert_chunk_to_generation_chunk`，非流式通常叫
     `_create_chat_result`），重写后 `super()` 调用父类逻辑，再从原始
     dict 里补字段。
   - 请求方向需要回填某个字段到历史消息（如 DeepSeek 的
     `reasoning_content` 续接）→ 重写 `_get_request_payload`，参考
     `patched_deepseek.py`。

2. **在 `settings.py` 加配置字段**（见 2.2），并同步更新 `.env.example`。

3. **在 `model_factory.py` 加一个 provider 分支**：
   - 常量：如果新 provider 有多个别名（如 vLLM 场景的 `{"vllm", "qwen"}`），
     用 `frozenset` 定义在模块顶部。
   - 分支顺序：`create_chat_model` 内的 `if/elif` 是按写下的顺序匹配的，
     新分支要放在通用兜底的 `init_chat_model(...)` 之前。
   - `thinking_enabled` 如果对新 provider有意义，翻译成该 provider 的
     请求格式（`extra_body` 字段名、模型名切换等，参考 3.1/3.2 两种已有
     写法）；如果新 provider 不支持思考模式，直接忽略这个参数即可，不需要
     报错。

4. **如果新 provider 的思考内容字段和 `reasoning_content` 不同**，在
   `chat_pipeline.py::_handle_ai_message` 里补一个分支，或者在
   `PatchedChatFoo` 里把字段名统一转换成 `reasoning_content`（更推荐，
   这样下游不需要感知新 provider 的存在）。

5. **补单元测试**：
   - `test/model/test_model_factory.py`：新增一个
     `test_foo_provider_builds_xxx` 用例，验证 provider 分支能正确路由、
     参数能正确透传（mock 掉 `PatchedChatFoo`/`init_chat_model` 本身，
     不发真实网络请求）。
   - 如果新建了 `patched_foo.py`：参考 `test_patched_vllm.py` 的写法，
     直接调用 `_convert_chunk_to_generation_chunk`/`_create_chat_result`
     等方法，喂假造的原始响应 dict，断言 `additional_kwargs` 里出现了
     预期字段——不要 mock 掉被测的方法本身。

6. **跑测试**：本地没有直接可用的 Python 环境时用
   `diit-agent-server` 这个 conda 环境（`C:\Users\test\miniconda3\envs\
   diit-agent-server\python.exe`，已装好本仓库匹配的 pytest/langchain
   版本）：
   ```bash
   "C:\Users\test\miniconda3\envs\diit-agent-server\python.exe" -m pytest test/model/ test/ -q
   ```

## 5. 常见坑清单（接入新 provider 时逐条自查）

- [ ] 新 provider 的响应里，思考内容/推理过程字段名是什么？是否是标准
      OpenAI 协议字段？如果不是，`ChatOpenAI`/`init_chat_model` 默认会
      静默丢弃它（见 3.2），必须显式处理。
- [ ] 新 provider 是否要求多轮对话里 assistant 消息携带某个"上一轮状态"
      字段（如 DeepSeek 的 `reasoning_content` 续接）？如果是，需要在
      请求序列化阶段（`_get_request_payload`）回填。
- [ ] `SystemMessage` 在新 provider 的消息序列里是否有位置要求（Qwen/vLLM
      的 chat template 强制要求 system 消息必须在最前面，非开头位置会
      触发 `400 System message must be at the beginning`）？如果有，
      确认所有会往持久化消息历史里插入内容的代码路径（中间件的
      `aafter_agent`、记忆压缩摘要等）都没有在非开头位置插入
      `SystemMessage`——本项目的教训是统一用 `AIMessage` 或
      `request.override(system_prompt=...)`（后者只影响单次调用，不写入
      持久化历史）来规避这个问题，不要用 `SystemMessage` 追加到消息列表
      末尾。
- [ ] API Key 允许为空吗？本地部署（如 vLLM）通常不校验，但 LangChain
      的模型类可能要求该字段是非空字符串，需要传占位符（参考 `"EMPTY"`）。
- [ ] 是否需要绕开代理？如果部署环境的 shell 有 `ALL_PROXY`/`HTTP(S)_PROXY`
      而新 provider 需要直连，参考 DeepSeek 分支用
      `httpx.Client(trust_env=False)`。
- [ ] `thinking_enabled=True` 时，新 provider 是切换到另一个模型、还是
      对同一个模型加请求参数？两种模式的选型逻辑都已经在 `model_factory.py`
      里实现（参考 `has_separate_thinking_model` 那段），新 provider
      如果语义相同可以直接复用同一套判断，不需要重新发明。
