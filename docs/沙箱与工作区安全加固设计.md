# 沙箱与工作区安全加固设计

> 状态：分阶段实施中，尚未全部实现。本文以当前 `ThreadWorkspace`、`PathGuard`、
> `LocalSandbox`、`DockerSandbox` 实现为基线；“现状”表示代码已实现，
> “目标”表示后续改造要求，不能在对外说明中混为一谈。

## 1. 目标与非目标

本设计要建立四条可验证的安全边界：

1. 一个用户不能访问其他用户的工作区。
2. 一个会话不能访问其他会话的 `workspace/uploads/outputs`。
3. 不可信代码不能直接接触宿主机文件系统、服务端密钥和内部网络。
4. 单次任务不能通过 CPU、内存、进程数、磁盘或输出占用拖垮服务。

Local Provider **仅用于开发者本地测试**，不属于任何线上部署选项，也不承诺执行
不可信代码。测试、预发布和生产等所有线上环境必须使用 Docker Provider；若配置为
Local、Docker daemon 不可用、镜像不可用或安全策略初始化失败，应用必须启动失败，
不得以告警后继续、按请求切换或静默降级的方式转入 Local。

## 2. 当前基线与缺口

### 2.1 已实现

- 工作区按 `{WORKSPACE_ROOT}/users/{user_id}/threads/{conversation_id}` 分区。
- 每个会话包含 `workspace`、`uploads`、`outputs` 三个固定目录。
- 文件工具通过 `PathGuard` 做相对路径解析和路径穿越校验。
- Local 命令固定 `cwd`、过滤默认环境变量、限制超时和 stdout；POSIX 下限制地址空间。
- Docker 命令使用一次性容器，工作区读写挂载、项目目录只读挂载，并设置内存上限。
- Provider 调用使用 `acquire -> try/finally -> release` 结构。
- 非 development 环境强制 Docker，Local 或未知 Provider 会阻止应用启动。
- Docker 初始化执行 daemon ping 和本地镜像校验，失败时不进入 ready、也不降级 Local。
- 会话和用户目录 ID 使用严格白名单，并对最终会话根路径做二次根目录约束。
- Docker 已启用断网、只读根文件系统、非 root、capability 全移除、
  `no-new-privileges`、内存/swap/CPU/PID/tmpfs 限制。
- Local 与 Docker 均同时限制 stdout 和 stderr 的返回大小。
- Docker 已通过权限为 `0600` 的一次性输入文件桥接 stdin，命令参数不参与 shell
  字符串拼接，容器结束或创建失败后都会清理输入文件。

### 2.2 必须补齐的缺口

| 编号 | 缺口 | 风险 | 目标措施 |
|---|---|---|---|
| G1 | `user_id/conversation_id` 直接参与目录拼接 | 会话根目录本身可能路径逃逸 | 可信身份解析、ID 白名单、最终根路径二次校验 |
| G2 | Local 进程仍可访问宿主机绝对路径和网络 | 不能承载不可信代码 | 明确可信等级；不可信执行强制 Docker |
| G3 | Docker 默认网络、CPU、PID、权限未收紧 | 横向访问、fork bomb、资源争抢 | 断网、CPU/PID 限制、非 root、降权、只读根文件系统 |
| G4 | Docker 只读挂载整个项目根目录 | 暴露无关源码和配置文件 | 仅挂载单个 Skill 的最小运行包 |
| G5 | `extra_env` 可重新注入任意敏感变量 | 密钥授权边界依赖调用方自律 | Capability 型密钥授权及环境变量最终校验 |
| G6 | stderr、磁盘和文件数量未限额 | 上下文/磁盘耗尽 | 双流限制、会话配额、单文件及 inode 数限制 |
| G7 | 工作区缺少 TTL、删除和孤儿清理 | 数据无限保留、隐私风险 | 状态机、异步清理、定期回收、保留策略 |
| G8 | Docker stdin 不可用 | 脚本型 Skill 在 Docker 下失败 | 临时输入文件协议或受控 attach stdin |
| G9 | 文件写入缺少并发和原子性约束 | 半写文件、覆盖竞态 | 临时文件 + 原子替换 + 乐观并发控制 |
| G10 | 缺少统一审计事件 | 越权和异常难追踪 | 文件/命令/容器/密钥使用统一审计 |

## 3. 信任分级与 Provider 路由

每次执行都必须带 `ExecutionPolicy`，禁止仅由模型选择 Provider：

```python
class ExecutionPolicy:
    trust_level: Literal["trusted", "untrusted"]
    network_profile: Literal["none", "egress_allowlist"]
    secret_names: frozenset[str]
    timeout_seconds: int
    cpu_limit: float
    memory_mb: int
    pids_limit: int
    output_bytes: int
```

路由规则：

| 来源 | 信任等级 | Provider |
|---|---|---|
| 仓库内、版本锁定、代码评审过的核心 Skill | trusted | 仅本地开发/测试可 Local；线上强制 Docker |
| 用户上传脚本、模型生成代码、运行时下载代码 | untrusted | 只能 Docker |
| 需要服务端密钥的 Skill | trusted + capability | Docker 优先，按声明注入最小密钥集 |

线上环境不允许 Provider 路由：Provider 在应用启动阶段固定为 Docker。若 Docker 不可用，
应用直接启动失败。运行过程中 Docker 暂时不可用时，当前请求返回
`SANDBOX_UNAVAILABLE`，不得自动切换到 Local。

启动校验采用 fail-closed 规则：

```python
if settings.CURRENT_ENV != "development" and settings.SANDBOX_PROVIDER != "docker":
    raise RuntimeError("线上环境必须使用 DockerSandboxProvider")
```

实际实现还应完成 Docker daemon 握手、镜像 digest 校验和安全配置自检；任一失败均阻止
应用进入 ready 状态。部署探针必须区分 liveness 与 readiness，Docker 执行能力未就绪时
不得接收业务流量。

## 4. Workspace 安全模型

### 4.1 身份与目录键

`user_id` 必须来自服务端认证上下文，禁止信任请求体、WebSocket 消息或模型参数中的
同名字段。`conversation_id` 必须先校验归属关系，再用于获取工作区。

磁盘目录不直接使用原始 ID，推荐使用稳定不可逆目录键：

```text
user_key   = base32(HMAC(workspace_key, tenant_id + ":" + user_id))[:32]
thread_key = base32(HMAC(workspace_key, user_id + ":" + conversation_id))[:32]
```

这样可以同时避免路径控制字符、超长名称和敏感业务 ID 泄露。若暂不引入 HMAC，最低
要求是只允许 `[A-Za-z0-9_-]{1,64}`，并对最终 `thread_root.resolve()` 再做一次
“必须位于 `WORKSPACE_ROOT` 内”的校验。

### 4.2 虚拟路径规范

对外统一三种显式 URI，不暴露宿主机路径：

```text
workspace://reports/summary.md
uploads://input.pdf
outputs://result.pptx
```

解析顺序必须固定：解析 scheme → 拒绝 NUL/绝对路径/非法编码 → 规范化 →
按目录根执行 `PathGuard` → 打开文件。禁止调用方自行拼接 `../uploads`。

路径守卫应防范符号链接竞态。写操作不能只做 `Path.resolve()` 后再普通打开；应优先使用
目录句柄相对打开和 `O_NOFOLLOW`（POSIX），或在创建/替换前后复核父目录与目标路径。
工作区内默认禁止 Agent 创建符号链接、junction 和 hard link。

### 4.3 文件访问能力

目录权限按最小能力划分：

- `workspace`：当前执行可读写。
- `uploads`：沙箱默认只读；上传 API 可写。
- `outputs`：沙箱可创建产物，但下载 API 只接受数据库登记过的 artifact ID。
- Skill 代码：只读且仅挂载当前 Skill 包。

文件写入采用 `.<name>.tmp-{uuid}` 临时文件、`fsync`、同目录原子替换。覆盖已有文件时
支持 `expected_version/expected_hash`，与 Read-Before-Write Middleware 配合避免并发覆盖。

### 4.4 配额和生命周期

建议默认值：

| 项目 | 默认值 |
|---|---:|
| 单上传文件 | 20 MiB |
| 单生成文件 | 50 MiB |
| 单会话总量 | 500 MiB |
| 单会话文件数 | 2,000 |
| 活跃工作区 TTL | 7 天 |
| outputs 保留期 | 30 天，可按业务覆盖 |

工作区状态为 `ACTIVE -> DELETING -> DELETED`。删除会话时先在数据库中切换为
`DELETING` 并拒绝新执行，再终止关联执行、删除文件、删除 artifact 元数据，最后标记
`DELETED`。后台任务定期回收过期、无数据库归属和停留在 `DELETING` 的孤儿目录。

## 5. Docker 执行边界

### 5.1 容器配置

生产 Docker Provider 至少应使用以下限制：

```text
network_disabled=true                 # 默认无网络
mem_limit=<policy.memory_mb>
memswap_limit=<same as mem_limit>     # 禁止额外 swap
nano_cpus=<policy.cpu_limit>
pids_limit=<policy.pids_limit>
read_only=true
cap_drop=["ALL"]
security_opt=["no-new-privileges:true"]
user=<non-root uid:gid>
tmpfs=/tmp:size=64m,noexec,nosuid,nodev
```

同时禁用 privileged、宿主机 PID/IPC/network namespace、Docker socket、设备映射和新增
capability。部署环境支持时增加 seccomp/AppArmor；更高风险场景使用 gVisor/Kata 或
远程沙箱服务，而不是继续堆叠 Local 限制。

挂载收敛为：

```text
workspace -> /workspace          rw, nodev,nosuid
uploads   -> /uploads            ro,nodev,nosuid,noexec
outputs   -> /outputs            rw,nodev,nosuid,noexec
skill pkg -> /opt/skill          ro,nodev,nosuid
```

不得再默认挂载整个 `PROJECT_ROOT`。Skill 加载阶段生成最小运行包，包含入口脚本及经过
声明的依赖文件，并记录内容摘要用于审计。

### 5.2 网络策略

默认完全断网。确需联网的 Skill 必须声明逻辑服务名，由受控 egress proxy 做域名、端口、
协议和请求大小限制；容器不能直接访问宿主机、云 metadata 地址、RFC1918 内网和 Docker
网关。授权基于 Skill ID，不接受模型传入任意域名临时放行。

### 5.3 输入输出协议

统一执行请求使用 JSON envelope。为解决 Docker stdin 缺口，短期将参数写入工作区内权限
为 `0600` 的一次性输入文件，容器通过固定参数 `--input /run/input/request.json` 读取；
执行结束无论成功失败都删除。长期可实现 docker attach stdin，但不能因此开放 shell。

stdout、stderr 分别执行字节上限，容器日志读取使用流式计数，达到上限立即停止或终止容器，
避免先在内存中完整读取再截断。工具返回只包含状态、退出码和头尾预览，完整日志按配额落盘。

### 5.4 超时与回收

区分启动超时、运行超时和清理超时；只有真正的 deadline exceeded 才返回 `TIMEOUT`，
Docker daemon、镜像、权限和运行时错误使用独立错误码。容器创建时添加执行 ID、用户键、
会话键、过期时间标签。除 `finally remove(force=True)` 外，后台 reaper 根据标签清理孤儿容器。

## 6. Local Provider 加固边界

Local 仅保留给开发者本地测试，不能出现在测试、预发布、生产或其他线上环境。即使只执行
可信脚本，线上也必须使用 Docker。Local 补充以下保护：

- 启动时校验 `CURRENT_ENV=development`；否则选择 Local 立即启动失败。
- 配置项 `LOCAL_SANDBOX_ALLOW_UNTRUSTED=false` 固定且不可由请求覆盖。
- Windows 使用 Job Object 限制内存、CPU 时间并终止整个进程树；POSIX 使用独立进程组，
  超时杀死进程组而不只是父进程。
- stdout/stderr 同时流式限额，避免 `communicate()` 内存膨胀。
- 命令使用可执行文件 allowlist；生产默认关闭通用 `run_command`。
- 日志和 UI 明确展示“Local 非强隔离”，不得命名为 secure execution。

即使完成这些加固，Local 仍不能替代容器或远程沙箱。

## 7. 密钥与环境变量

密钥注入遵循三重交集：

```text
实际注入 = Skill.required_secrets
         ∩ 用户/租户已授权 secrets
         ∩ 当前执行策略允许 secrets
```

模型只能引用逻辑密钥名，不能提供密钥值。Sandbox 在最后一步从 Secret Provider 获取值，
通过内存或一次性文件注入；不写入 workspace，不进入命令参数，不进入审计正文。环境变量经过
基础过滤、显式 allowlist 和危险键复核三层处理，调用方的 `extra_env` 不能绕过最终 denylist。

对 stdout、stderr、异常和工具结果做密钥值指纹脱敏。一次执行结束后销毁临时凭证，并记录
“使用了哪个逻辑密钥”，但不记录值。

## 8. 授权、审计与可观测性

每个文件和执行请求都携带不可伪造的 `ExecutionContext`：

```text
request_id, execution_id, tenant_id, authenticated_user_id,
conversation_id, tool_name, skill_id, policy_id
```

执行前检查：会话归属、工具权限、Skill 权限、目录能力、密钥能力和资源策略。审计事件至少包括：

- workspace 创建、配额拒绝、过期和删除；
- 文件读取、写入、覆盖、下载，记录虚拟路径、大小和摘要；
- 命令开始/结束、镜像 digest、Skill digest、资源上限、状态和耗时；
- Docker 创建、kill、remove、reaper 清理；
- 密钥逻辑名授权/拒绝；
- 路径穿越、符号链接、越权会话和网络策略拦截。

日志不得记录文件全文、密钥值和宿主机绝对路径。对路径穿越、跨会话访问、容器清理失败、
配额连续触发建立告警。

## 9. 接口演进

建议把现有 Provider 接口演进为显式请求对象：

```python
sandbox = await provider.acquire(execution_context, execution_policy)
result = await sandbox.execute(ExecutionRequest(
    argv=["python3", "/opt/skill/main.py"],
    stdin_json=args,
    mounts=declared_mounts,
))
```

文件 API 使用 `VirtualPath` 值对象，禁止业务层传裸字符串和 `WorkspaceDirectory` 任意组合。
`CommandResult` 增加稳定错误码：`SUCCESS`、`EXIT_NONZERO`、`TIMEOUT`、
`OUTPUT_LIMIT`、`RESOURCE_LIMIT`、`POLICY_DENIED`、`RUNTIME_UNAVAILABLE`、
`INTERNAL_ERROR`。Agent 仍接收可理解的工具文本，但监控与重试依据结构化状态，而不是解析文案。

## 11. 验收标准

以下测试全部通过才可宣称具备“不可信代码隔离”能力：

1. `../`、绝对路径、编码变体、symlink/junction 均不能越出三个目录。
2. 伪造 `user_id/conversation_id` 不能访问或推断其他工作区。
3. 容器无法读取宿主机项目配置、Docker socket、其他会话目录和云 metadata。
4. fork bomb、内存膨胀、无限输出、无限写盘、超时子进程均被限制并完整回收。
5. 未声明、未授权或策略不允许的密钥均不会进入容器和日志。
6. Docker daemon 不可用时，不可信执行明确失败且不降级 Local。
7. 并发覆盖、执行中删除会话和服务崩溃后重启不会产生可继续访问的半成品或孤儿资源。
8. 每次执行均能通过 `execution_id` 关联授权、文件、容器、日志与最终状态。
9. 任何非 `development` 环境配置 Local、Docker 初始化失败或镜像校验失败时，应用均不能
   进入 ready 状态；自动化部署测试证明不存在 Local 降级路径。
